# 增长闭环教程：把"加购未支付"的用户拉回来

数据面教程（[analytics-tutorial.md](analytics-tutorial.md)）解决了"看见"问题，本篇解决"**行动**"问题：
以一个经典运营任务为主线——**圈出加购未支付的用户 → 触达他们 → 用 AB 实验验证挽回策略 →
用告警守住转化大盘 → 用定时报告沉淀周报**——走通增长闭环的全部模块。

> 行文同前两篇：任务意图 + 菜单路径，不绑定控件坐标。菜单名以当前 main 后台为准。

## 0. 主线任务

> **漏斗分析发现 add_to_cart → pay_success 流失 60%。圈出这批人，定向发券挽回，**
> **用 AB 实验验证"发券 vs 不发券"哪种策略有效，并配告警监控转化率。**

## 一、圈人：用户分群

菜单：**增长运营 → 用户分群**（`/segments`）

1. 新建分群，条件按事件 + 属性圈人：
   - **做过** `add_to_cart`（近 7 天）
   - **未做过** `pay_success`（近 7 天）
2. 保存后分群**定时刷新**，人群是动态的：有人支付了会自动出群，新加购未付的自动进群；
3. 圈出来的人群规模、个体明细可在分群详情查看。

> 分群也是 [数据分析 → 基础分析 → 用户分群](analytics-tutorial.md) 的入口之一；
> 更细的用户画像可用「数据配置 → 标签管理」（标签定义 / 用户标签 / **ID 映射**——把同一个人在
> 多端多账号的 identity 串起来，跨端归因的前提）。

## 二、触达：通知体系 + 营销触达

发消息前先搭好通道（菜单在 **风控与通知 → 通知管理**，`/risk-notification` 下）：

1. **通知渠道**：接入短信/邮件/Webhook 等通道，配凭据；
2. **通知模板**：变量化的文案模板（如 `{{userName}}，您购物车的 {{productName}} 已降价`）；
3. **通知路由规则**：什么事件/条件走哪个渠道哪个模板；
4. **通知投递记录**：每条消息的投递状态（成功/失败/重试）——排查"用户说没收到"就看这里。

然后创建触达任务，菜单：**增长运营 → 营销触达**（`/campaigns`）：

- 人群选第一节建的分群（加购未支付）；
- 动作选通知渠道 + 模板（发券文案）；
- 上线后投递结果在任务详情与投递记录里对账。

## 三、验证策略：AB 实验（与 SDK 打通）

菜单：**增长运营 → 功能开关 / AB实验**（`/feature-flags`）

**实验设计**：把分群用户随机分两组——A 组发券（实验组），B 组不发（对照组），
对比两组的 `pay_success` 转化率。

**关键机制：开关如何到达客户端**——

1. 后台创建开关/实验（如 `checkout_coupon`），配置分流比例与变体（`control` / `coupon`）；
2. 各端 SDK 拉取并使用：

```ts
// 各端 API 同名（此处 Web SDK 示例，Go/Java/Python/Flutter/Android/iOS/C++/ArkTS 一致）
await uba.loadFlags();                    // 拉取 {checkout_coupon: "coupon"}
const variant = uba.getFlag('checkout_coupon');  // 读变体 + 自动上报 $feature_flag 曝光
if (uba.isFeatureEnabled('checkout_coupon')) {
  showCoupon();                           // 实验组才展示发券 UI
}
```

3. **曝光即归因**：SDK 的 `getFlag()` 会自动上报 `$feature_flag` 事件（每会话每开关一次，
   `eventCategory: experiment`，带 `flag_key`/`variant`）——分析侧用它把"用户属于哪组"
   和"该组转化率"对上，不需要你手工打分流标签；
4. **服务端分流**：flags 接口按 `deviceId`（+登录后 `userId`）确定性分流，同一用户每次拉取
   得到相同变体，实验期内分组稳定。

> 各端接入细节：[接入指南 §二](sdk_integration.md#二sdk-选型) 选端进入对应文档；
> 曝光去重与采样行为见各端 README 的「AB 实验开关」节。

## 四、守住大盘：告警中心

菜单：**增长运营 → 告警中心**（`/alert`）

挽回上线后，配一条告警防止策略本身把大盘打坏：

- 监控对象：`pay_success` 事件量 / 漏斗转化率（阈值或环比波动）；
- 触发动作：走第二节的通知渠道推送到值班群（Webhook 类渠道最适合）；
- 异常波动也可先用 **数据分析 → 深度洞察 → 异常检测** 做回溯诊断（哪些事件 PV 暴涨暴跌，
  是否疑似埋点丢失）。

风控侧的实时处置（风险事件→自动拦截/人工处置/Webhook 回调）在 **风控与通知 → 风控管理**
（事件 / 规则 / Webhooks）——规则用 CEL 表达式定义（demo 数据里有现成示例），与本篇的营销
触达共用通知体系，但语义是"挡坏人"而非"拉用户"。

## 五、沉淀周报：定时报告

菜单：**增长运营 → 定时报告**（`/report-subscriptions`）

把每周要人肉跑的数字固化：

- 订阅内容：漏斗/留存/付费分析等已保存的分析（或看板）；
- 推送：定时投递到邮件/Webhook 渠道（复用通知渠道配置）；
- 组合投屏：大盘数字日常盯 **自定义看板**（`/custom-dashboards`）与 **实时大屏**。

## 六、闭环回顾

```
漏斗发现流失 → 用户分群圈人 → 通知渠道/模板/路由 → 营销触达执行
     ↑                                              │
     │        AB 开关(后台) ⇄ SDK loadFlags/getFlag ─┘ 曝光自动归因
     │                                              │
告警中心守住大盘 ← 实验结论反哺策略 ← 定时报告沉淀周报 ← 转化率对比
```

每一环的细节字段与协议见 [SDK 接入指南](sdk_integration.md)；AI 加持（智能问数直接用自然语言
查数、知识库沉淀运营 SOP）见 [AI 助手教程](ai-tutorial.md)。

## 七、坑与提示

- **先配渠道再建任务**：营销触达/告警/定时报告的出口都是通知渠道，渠道凭据不通全链路都空转；
- **分群是动态的**：条件口径写错（如把"未支付"限定窗口写漏），人群会漂移——上线前先看一眼
  分群明细抽查；
- **AB 实验别手工分组**：一切以后台开关 + SDK 曝光事件为准，手工标签无法与曝光对齐；
- **通知投递失败**：优先查投递记录的状态与渠道凭据有效期（模板变量名写错也会在这暴露）。
